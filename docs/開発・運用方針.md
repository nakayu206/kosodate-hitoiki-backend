# 開発・運用方針

更新日：2026-09-29。実行環境・CI・デプロイ手順は未構築。

## 1. ブランチ

**決定済み（2026-09-29）**：フロントエンドの[環境とブランチ運用ガイド](https://github.com/nakayu206/kosodate-hitoiki/blob/main/docs/環境とブランチ運用.md)に合わせ、バックエンドもdevelopを使う。作業ブランチはdevelopから作成し、変更時は必ずPRを作成する。通常の変更をmain・developへ直接コミット・pushしない。

| ブランチ | 役割 |
|---|---|
| main | リリース済みの状態 |
| develop | 開発内容の統合先 |
| feature/*・fix/* | developから分岐し、develop宛てにPR |
| hotfix/* | mainから分岐し、修正をmain・developへ反映 |

参照ガイドはPRに最低1名の承認を要求している。バックエンドのレビュー担当・ブランチ保護設定は未定。空リポジトリの初期化のみ、内容を含まない初期コミットをブランチの共通起点にする。

## Issue・PRの運用

作業をIssueで管理し、PR本文の関連Issue欄で紐づける。今回の整備は[Issue #1](https://github.com/nakayu206/kosodate-hitoiki-backend/issues/1)。PR作成後、レビューを経てマージする。

Issueテンプレート（Bug・Logic・UI）とPRテンプレートは、kosodate-hitoikiの同名ファイルをそのまま使用する。テンプレートのチェック欄は実際の確認結果だけを記入し、対象外の検証には理由を添える。

PRのbaseがdevelopの場合、Issueの自動クローズはデフォルトブランチの設定に依存する。関連付けとクローズ状態はマージ時に確認する。

## 3. 変更・検証の方針案

DB変更はマイグレーションとして残し、既に適用した変更を直接書き換えず、新しい変更で追従する。空のDBからの構築と、既存データがある状態からの更新を確認する。

実装時には次の振る舞いを重点的に検証する。

- 未ログインでコメント本文・プロフィール本文・共感件数を取得できない。
- 他人の投稿・コメント・プロフィールを変更できない。
- 受付終了・ブロック・利用停止時に、APIを直接呼んでも制限が働く。
- 返信の階層、文字数、ニックネーム・通報等の重複制約を守る。
- 同時リクエストでも共感・通報の件数やニックネーム予約が壊れない。
- 送信前チェックを迂回できず、編集時にもチェックする。
- 投稿削除・退会・途中失敗からの再実行が保持要件と整合する。
- 管理操作に運営者権限と二段階認証を要求する。

CIの実行コマンドは実装に合わせて追加する。ドキュメントのみの段階ではリンクと内容の整合を確認する。

## 4. 秘密情報・ログの方針案

APIキー、特権キー、認証用秘密情報をGitへ保存しない。設定例には変数名と用途だけを記載する。投稿本文や認証情報をエラーログへ無条件に出力しない。特権を使う処理は呼び出し元の本人確認・権限確認を明示する。

## 5. バックアップと復旧

**決定済み**：無料プランでの開始にあたり、自前の定期バックアップを必須とし、暗号化して非公開で保管する。削除済みデータも一定期間でバックアップから消えるようにする。

未決定：取得頻度、保持期間、保管先、対象データ、暗号鍵の管理、復旧目標、失敗の通知先。

**設計案**：バックアップが取得できたことに加え、隔離した環境で復元できることを確認する。退会・削除済みデータが復元によって再公開されない手順を定義する。DB以外の認証設定・秘密情報など、別途復旧が必要なものを洗い出す。

料金・無料枠・一時停止条件は変わりうるため、環境構築時に公式情報を確認する。本資料は現行料金や利用可能機能を保証するものではない。
