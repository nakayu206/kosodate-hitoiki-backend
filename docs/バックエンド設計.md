# バックエンド設計

更新日：2026-09-29。要件は決定済み、実現方式は明記したものを除き設計案。

## 1. 担当範囲と構成

**決定済み**：Flutterアプリとバックエンドを別リポジトリで管理し、バックエンドにSupabaseを採用する。無料プランで開始し、必要になった段階で有料プランを検討する。

| 領域 | このリポジトリで扱う内容 |
|---|---|
| DB | テーブル、制約、インデックス、マイグレーション |
| 権限 | RLS、公開可能な項目、本人・運営者の操作範囲 |
| 認証 | メール・Google・Appleログインに必要なバックエンド設定 |
| サーバー処理 | 送信前チェック、投稿等の保存、退会処理、運営操作 |
| 通知 | 通知データ、通知設定、プッシュ配信処理 |
| 運用 | 通報対処記録、バックアップ、復旧手順 |

管理画面のUI実装先は未決定。本リポジトリでは管理画面が利用する権限・データ操作を扱う。

**設計案**：通常の読み取りはRLSで保護したDBアクセスを基本とし、外部APIを利用する処理はEdge Functions、複数データを不可分に更新する処理はDB関数・トランザクションに集約する。具体的なAPI名・引数・レスポンスは今後定義する。

## 2. 閲覧と操作の境界

以下は決定済み要件。画面上の非表示だけで済ませず、DB・APIからも取得や操作を拒否する。

| 対象 | 権限・条件 |
|---|---|
| 公開状態の投稿本文・コメント件数・投稿本文検索 | 未ログインでも利用可 |
| コメント・返信本文、プロフィール本文 | ログイン必須 |
| 投稿上のニックネーム | 公開表示。プロフィール本文とは権限を分ける |
| 投稿・コメントの作成 | ログイン必須。受付状態・ブロック等も確認 |
| 投稿・コメント・プロフィールの編集 | 本人のみ。文章は編集時も送信前チェック |
| 共感の件数 | 投稿者のみ閲覧可 |
| 保存一覧 | 保存した本人のみ。他者へ保存数・通知を公開しない |
| ミュート・ブロック設定 | 本人が管理。相手へ通知しない |
| 通報・対処記録 | 相手へ通報者情報を公開しない。運営者の参照範囲は詳細設計で定義 |
| 管理操作 | 運営者のみ。二段階認証必須 |

共感の登録要否は未決定。権限表の空白を推測で補わず、実装前に確定する。

**設計案**：公開投稿の取得経路に認証情報・プロフィール本文・共感件数・通報情報を含めない。ビューやDB関数でもRLSを意図せず迂回しないように権限を検証する。特権キーはアプリへ配布しない。

## 3. 投稿・コメント

**決定済み**：投稿種類は「ぐち」「相談」「コツ／体験談」。話題は任意で1つ。一覧は新着順のみ。

| 項目 | 制約 |
|---|---|
| 投稿本文 | 1,000文字まで |
| コメント・返信 | 500文字まで。返信は1段階のみ |
| ニックネーム | 2〜12文字、重複不可、30日に1回変更可 |
| 自己紹介 | 任意、100文字まで |

空入力の拒否は受入条件案。空白の扱い・文字数の数え方は未決定。

反応モードとコメント受付状態は別の概念として管理する。

| 状態 | 新規自由コメント・返信 | 既存コメント |
|---|---|---|
| ただ聞いてほしい（初期値） | 不可 | 逆方向のモード変更が未決定のため扱いも未確定 |
| 話を聞きたい・受付中 | 条件を満たすログイン利用者が送信可 | ログイン後に閲覧可 |
| 話を聞きたい・受付終了 | 不可 | 残してログイン後に閲覧可 |

投稿者は「ただ聞いてほしい」から「話を聞きたい」へ変更でき、受付終了後も再開できる。離席による自動終了は行わない。受付終了後も共感ボタンは継続するが、定型文と既存コメントの編集の扱いは未決定。

**設計案**：保存時点で受付状態を確認し、受付終了前に開いた画面からの送信も拒否する。受付変更とコメント保存が同時に起きても制約を守れるトランザクションを設計する。

## 4. 送信前チェック

**決定済み**：投稿・コメント・返信・ニックネーム・自己紹介を対象とし、編集時にも実施する。禁止語リストとOpenAI Moderation APIで開始する方針。日本語の愚痴と攻撃の区別は公開前に実例で検証する。

他者への攻撃・差別・名前や個人情報は送信を防ぐ一方、自分のつらさを吐き出す表現は制限しない。自分や子どもへの危害をほのめかす書き込みは止めず、本人にのみ相談先を案内する。イニシャルや公人・作品名は機械的に禁止しない。

**設計案**：チェックを経た本文と実際に保存する本文が一致する経路を設ける。クライアントがチェック結果を自己申告したり、DBへ直接書き込んだりして迂回できないようにする。外部API呼び出し後、保存直前にも権限と受付状態を再確認する。

未決定：判定の閾値、個人情報検出の具体方式、確認表示後の再送、外部API障害時の処理、誤判定への対応。Moderation APIだけで全要件が満たせることは未検証。

## 5. ブロック・通報・運営

**決定済み**：AがBをブロックすると、AにはBの投稿・コメント・返信を表示せず、BはAの投稿・コメントへのコメント・返信・共感ができない。投稿本文は公開されるため、BからAの投稿を完全に隠す仕様ではない。

異なる3人から通報された投稿・コメントは自動で一時非表示にする。同一人物の重複通報で件数を増やさないことは受入条件案。運営は再表示・削除・警告・利用停止を行い、削除時は本人に理由を通知する。対処操作を自動記録する。

**設計案**：通報の一意制約とトランザクションで同時通報を扱う。一時非表示は一覧・検索・詳細など各取得経路で適用する。再表示後の通報集計方法、親投稿が非表示のときのコメントの扱いは実装前に確定する。

## 6. 通知・削除

**決定済み**：自由コメントは投稿者へ個別通知、共感はまとめて通知する。利用者は通知を停止できる。集約頻度・返信通知・配信サービスは未決定。

投稿削除時はコメント・返信・共感も削除する。退会時は投稿・コメント・プロフィール・保存投稿を削除し、ニックネームは30日間他者が再利用できないようにする。通報対処記録とバックアップは別途定める期間を経て削除する。
