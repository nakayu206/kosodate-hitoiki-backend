# データ設計案

更新日：2026-09-29。**この文書のテーブル名・分割・実現方式はすべて設計案**。SQLを作成する前に、権限と未決事項を含めて確定する。

## 1. データの候補

| データ候補 | 役割・主な関係 |
|---|---|
| profiles | 認証ユーザーに対応する表示名、アイコン、自己紹介、子どもの年齢帯 |
| nickname_reservations | 変更前・退会時のニックネームと再利用禁止期限 |
| posts | 投稿者、種類、任意の話題、本文、反応モード、受付状態、公開状態、作成・編集日時 |
| topics | 運営が用意する話題一覧 |
| comments | 投稿、投稿者、本文、親コメント、公開状態、作成・編集日時 |
| reaction_types | 運営が用意する定型文。共感ボタンと統一した単一のリアクション種別として扱う（決定済み） |
| reactions | 投稿・利用者ごとに1件、reaction_typesを選択して記録。ログイン必須、変更・取消可能。識別方法（unique制約の設計）は#9で確定 |
| saved_posts | 利用者と保存対象投稿の組み合わせ |
| hidden_items | 本人だけに非表示とする投稿・コメント |
| blocks | ブロックした利用者と対象利用者の組み合わせ |
| muted_topics / muted_words | 利用者ごとのミュート設定 |
| reports | 通報者、対象、理由、補足、日時 |
| moderation_actions | 運営者、対象、対処内容、理由、日時 |
| account_restrictions | 警告・利用停止等の状態。利用停止は段階的（初回7日→再発30日→無期限）。判定基準・異議申立て窓口は未確定 |
| notifications / notification_settings | 本人向けのお知らせ、既読状態、通知設定 |
| push_devices | 配信先端末。採用する配信方式に合わせて定義 |
| app_settings | 登録直後のレート制限件数・新規登録停止フラグなど、運営がコード変更なしで調整する設定値（決定済み：設定テーブル方式を採用） |

認証情報はSupabase Authで管理する想定。公開用データへメールアドレスなどを複製しない。公開ニックネームの取得と会員限定プロフィールの取得を分ける。

## 2. 保存時に守る制約

| 対象 | 要件・設計上の論点 |
|---|---|
| 投稿・コメント | 文字数上限、本人のみ編集・削除、編集日時の更新 |
| 返信 | 親コメントは同じ投稿に属すること。返信への返信を禁止 |
| コメント保存 | 反応モード、受付状態、ブロック、利用停止の確認 |
| ニックネーム | 同時登録でも重複不可。変更間隔と旧名予約を同時に検証 |
| 定型文 | 1投稿1人1つ、変更・取消可。共感ボタンと統一した単一リアクションのため併用の概念はない（決定済み） |
| 通報 | 同一通報者・同一対象はunique制約で1件に集約（決定済み）。3人到達時の非表示更新と整合させる |
| 保存・ブロック | 組み合わせの重複を防ぐ。解除・再操作を安全に扱う |

ニックネームは全角・半角、大文字・小文字、前後空白の違いを同一視して重複判定する（決定済み）。表示値と一意判定用の正規化値を分けて保持し、予約名にも同じ規則を適用する。絵文字等も1文字として数え2〜12文字とする。正規化の具体的なUnicode処理（NFKC等の採用可否）は#9で定義する。

## 3. 読み取りの設計

- 投稿一覧と検索は新着順を基本とし、ページ境界で重複・抜けを避けるため日時とIDを使ったページングを検討する。
- 日本語検索の方式は未確定。PGroonga等の可用性と要件を確認して選ぶ。
- 削除・一時非表示・本人の非表示・ブロック・ミュートを一覧と検索に適用する。投稿が一時非表示の場合はコメント・返信も一般利用者から隠す（決定済み）。
- 公開するコメント件数と、会員限定のコメント本文を分離する。削除済み・一時非表示のコメントは件数に含めない（決定済み）。コメントは古い順、返信は親コメントの下に表示する（決定済み）。
- 共感件数・保存情報・通報情報は、公開投稿の取得結果から漏れない構成にする。
- 本人・運営者・未ログイン利用者ごとに、一時非表示対象の取得可否を定義する。

## 4. 削除と保持

| 操作 | 決定済みの扱い | 設計時に詰める点 |
|---|---|---|
| 投稿削除 | コメント・返信・共感も削除。保存一覧からも消える | 通知・通報参照の扱い |
| コメント削除 | 本人が削除可能。親コメント削除時は本文を「削除済み」に置換し返信は残す | 実データ削除のタイミング、退会時の全体削除との整合 |
| ニックネーム変更 | 旧名を30日間他者が使用不可。本人は再利用可。過去投稿も新名で表示 | ― |
| 退会 | 投稿・コメント・プロフィール・保存投稿を削除、名前を30日予約 | 認証削除との整合、退会前確認表示・取消期間の要否 |
| 通報対処記録 | 1年保持して削除。退会後もこの期間は残す | 保存項目・閲覧権限 |
| バックアップ | 30日保持し、削除データも同期間で除去 | 復元時の削除済みデータの扱い |

通報記録1年・バックアップ30日は確定値として採用した（2026-09-29）。復元手順や削除バッチの実装は#21で扱う。

**設計案**：通常の関連データ削除と、保持すべき通報対処記録を区別する。退会は認証基盤とDBの両方にまたがるため、途中失敗時に再実行・完了確認できる手順を設計する。外部キーの一律CASCADEだけで保持要件を満たすと判断しない。
